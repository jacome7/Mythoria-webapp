# KeyInvoice recovery reservation contract

Last updated: 2026-11-09. Local implementation only; production application and real invoice issuance require separate approval.

Migrations 0046–0048 must be applied before either service uses the recovery contract. Mirror exact SQL types in admin. Migration 0048 locks the fiscal table, fails closed on duplicate `(provider, doc_type, coalesce(doc_series, ''), doc_num)` identities where doc_num is non-null, then creates the corresponding unique index. Null and empty series are the same identity. Investigate and reconcile duplicates before retrying; do not silently delete them. Run the migration transactionally. No migration has been applied by this change.

Recovery claims and worker claims must be atomic conditional updates of the same `fiscal_documents` row. The worker claims only `pending` or `failed` rows with recovery state NULL or `cancelled`, and refuses a document lacking `doc_num` if an `insert_document_requested` event exists. It increments `attempt_count` as a fencing generation and every worker document update requires the matching generation, `issuing` status, and an unblocked recovery state. There is deliberately no timed takeover of an `issuing` worker: an HTTP request can still complete after any timeout. Admin MUST refuse to reserve any `issuing` row, even if old, and must not reset it merely due to age. Recovery of such rows requires proving the worker and all outstanding remote calls have stopped, and separately reconciling KeyInvoice before changing state.

Admin reservation must compare-and-swap a non-issuing row, write a cryptographically random token's SHA-256 hash, owner, canonical payload SHA-256 hash, state `reserved`, and expiration together. Never store or log the raw token. Check token, owner, payload hash, state and expiration atomically on submission; transition to `submitted` before the remote operation. `submitted` remains blocked even after expiration or ambiguous failure until reconciled. Expiration never automatically unlocks a reservation. `cancelled` may be set only when no remote operation was submitted and the token is invalidated. Reconciliation records the verified remote identity before moving to `reconciled`; `reconciled` is not automatically retryable. All transitions must be conditional and audited. The permanent `recovery_tokens` ledger enforces global token uniqueness: primary key `token_hash` varchar(64), `fiscal_document_id` uuid (restrict FK), `actor` text, `payload_hash` varchar(64), and `state` varchar(16), all NOT NULL. Insert the ledger row and claim the document in one transaction; a duplicate token or failed claim must roll back both. Conditionally update both records together in every transition, matching document ID, token, actor, payload hash and prior state; check expiry on submission against the database clock. Retain ledger rows forever (including cancelled/reconciled), never overwrite or delete them. This retention and atomicity are application responsibilities, not enforced by a delete-prevention trigger.

Rollout requires a coordinated maintenance window: stop and drain **all old worker and webapp instances** capable of issuing documents, and establish that all their outstanding KeyInvoice calls have completed or been reconciled before enabling recovery or starting guarded workers. A rolling deployment with old workers still active is unsafe; database fencing cannot stop their remote calls. Apply migrations 0046–0048 and verify migration 0048's unique identity index is present before enabling either service. The database index, including its null/empty-series normalization, is the authoritative identity constraint; application pre-checks are not a substitute. Investigate duplicate identities before migration, without deleting records merely to make it pass.

The Admin side is implemented locally in fiscal-recovery.ts and its two MCP tools; see the sibling Admin docs/mcp.md. The opt-in Admin PostgreSQL integration suite tests the actual recovery transactions against this service's issueClaimPredicate/issueFence and migrations 0028 plus 0046-0048, using an isolated Unix socket and disposable database only. It validates the fiscal subsystem, not the entire application migration chain or production rollout. The contract cannot revoke an already dispatched external request using a database fence alone.
